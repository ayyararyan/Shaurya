# BKT — Backtesting

## Objective

Provide event-driven, causally valid replay against the same canonical tape as live, with measured latency, shared execution realism, honest walk-forward evaluation, explicit no-own-impact assumptions, and authoritative C++ reproduction before a result advances beyond exploratory (D14).

## Object and identification ledger

| Object | Category | Meaning / boundary |
|---|---|---|
| Historical canonical tape | Observed record | Preserves what DAT captured, including quality/missingness; it is not a complete market-by-order history. |
| Replay state and deterministic decisions | Deterministically derived | Given tape, configuration, and measured latency. |
| Own queue-ahead | Estimated, with reported bounds | Consumed from EXE-10. Exact at acceptance and bounded thereafter under D23; individual anonymous-order rank remains unidentified. |
| Simulated fills and ledger | Proxy | Generated by EXE-09 and never relabelled realised. |
| Decision latency | Observed measurement | Injected from live measurement distributions/records, never assumed as zero. |
| No-own-impact result | Scenario | Valid only under the declared size threshold; above it the result is labelled unreliable. |

## Architecture and contracts

- Consumes `CON-01` tape, `CON-07` timestamps, EXE-09/10 realism, and shared `CON-04` configuration.
- Produces canonical `CON-02` ledger rows so replay and live analytics share semantics.
- `NAT-07` C++ replay is authoritative. Python is a non-authoritative research-speed event loop.
- `BKT-05` is the required proof that the two implementations agree; sharing a tape schema alone is insufficient.

## Timing, causality, and safety gates

1. Deliver each event in recorded causal order and expose it only at receive time.
2. Apply the measured decision delay before order submission and subsequent exchange interaction.
3. Generate fills only through EXE-09 using EXE-10's labelled queue estimate.
4. Preserve gaps, stale data, and invalidated runs; replay cannot silently clean the tape.
5. A Python result remains exploratory until the same configuration reproduces in authoritative C++.
6. Every result declares no own impact and its reliability threshold.

## Outputs and acceptance tests

- Replay manifest, canonical ledger, configuration snapshot, measured-latency provenance, evaluation report, and no-own-impact declaration.
- Golden-tape determinism: repeated C++ runs produce byte/semantically identical outputs.
- Python/C++ parity requires identical fills and ledger rows or an explained, approved contract change.
- Leakage tests ensure decisions never observe post-decision events.
- Result status distinguishes exploratory Python output from authoritative reproduced output.

## Exclusions

- A separate backtest-only data format or fill model.
- Touch-fill assumptions.
- Assumed zero latency.
- A full own-order market-impact simulator (explicitly out under D14).
- Calling a Python-only result identification-grade.
