# Planning Interview Transcript

## Q1. What is authoritative when the implementation prompt and repository history differ?

The user's current request authorizes executing the attached implementation prompt end to end.
Repository code and the installed CLI are operational references, not new requirements. Existing
user changes remain untouched, and live broker/cloud actions remain prohibited.

## Q2. Should planning stop for discretionary architecture choices?

No. The specification is unusually complete and directs the workflow not to stop after planning.
Use evidence-backed, fail-closed decisions that preserve Data/Research boundaries and record any
unavoidable intentional parity difference. No additional product expansion is authorized.

## Q3. What counts as end-to-end given the prohibition on live actions?

A portable, fully tested shadow control plane with hermetic broker, transport, launch, and
reconciliation fixtures; a dormant live adapter compiled OFF; and an explicit live checklist.
Real authentication, order placement, AWS actions, and remote launch are skipped by design and
remain live-enablement blockers.

## Q4. How should existing dirty state be handled?

Use clean isolated worktrees from freshly fetched GitHub defaults. Do not stage, stash, delete, or
edit the dirty source checkout. Commit and push only intentional branch changes.
